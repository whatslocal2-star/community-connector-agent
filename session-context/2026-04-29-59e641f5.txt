## 1. Connecting to prolocaliq + localloop (the easy one)

Both apps just need HTTP calls to community-connector's Netlify URL. The surface is already there:

| Endpoint | Who calls it | What for |
|---|---|---|
| `POST /functions/chat` | prolocaliq chat widget, localloop `business-onboarding.tsx` | Onboarding conversation (no auth) |
| `GET /functions/admin` | prolocaliq member list | Discovery feed (bearer token) |
| `POST /functions/matches` | both apps | Similarity search / "people like you" (bearer token) |

The three things you'd actually need to wire:
- **Session ID** — prolocaliq uses localStorage UUID same as the current web UI; localloop stores it in AsyncStorage
- **CORS** — Netlify functions need to whitelist the prolocaliq/localloop origins (or open them)
- **Auth token** — `ADMIN_TOKEN` in an env var on both frontend apps for the protected endpoints

That's genuinely 1-2 days of work, no architecture decisions required.

## 2. The multi-agent architecture question (the harder one)

Here's the honest read based on what you've already built:

**mae_agent is already your answer** — Hono + Postgres + Drizzle + Mastra + Claude, Phase 5b done, multi-channel adapters, campaigns, human-in-loop, 10-table schema. It's the WhatsLocal multi-channel OS. You've already made the Mastra bet and it's working.

**The frameworks compared against what you actually need:**

| Framework | What it's actually for | Your situation |
|---|---|---|
| **Mastra** | Agent orchestration — tools, memory, multi-agent handoffs | Already in mae_agent. Good call. |
| **Trigger.dev** | Durable job execution — retries, scheduling, queues, human-in-loop pauses | **Complementary**, not competing. Fills the gap Mastra has for long-running workflows. pureflow proved the pattern. |
| **LangChain/LangSmith** | LangChain = agent framework (Python-native, heavy in TS). LangSmith = tracing/eval | LangSmith as observability layer on top of mae_agent is worth it. LangChain itself — skip, you'd be rebuilding what Mastra already gives you. |
| **TypeScript agents (bare)** | Full control, no framework overhead | Only worth it if Mastra becomes a ceiling. It hasn't. |

**The actual architecture question** is about the relationship between community-connector-agent and mae_agent:

**Option A — Keep them separate, wire via API (recommended now)**
community-connector stays a Netlify microservice. mae_agent calls it as a channel adapter when it needs to trigger an onboarding conversation. Clean seam, no migration needed.

**Option B — Absorb community-connector into mae_agent**
Long-term this makes sense — mae_agent already has the channel adapters, and community-connector's Firestore + Pinecone could be a mae_agent "memory backend." But it's a meaningful migration.

**Option C — Swap to a different framework**
No reason to. The Mastra + Trigger.dev combo covers your full surface: Mastra for agent logic, Trigger.dev for durable workflows and scheduling.

**My recommendation:** Don't change the stack. The Mastra choice in mae_agent is solid. Add Trigger.dev to mae_agent for durable scheduling/campaign workflows (it already has a demo in `pureflow` to reference). Keep community-connector as a standalone microservice for now, wire prolocaliq + localloop to its HTTP endpoints, and add a thin mae_agent → community-connector adapter so mae_agent can trigger onboarding sessions. That's the path of least resistance with the highest leverage.

## The Role Split

**Community Connector Agent** = the member-facing intelligence layer
- Conversational interface (web + SMS) — already built
- Profile building + semantic matching (Pinecone) — already built
- **Actions the agent can trigger** from conversation: subscribe to their social, schedule a follow-up, add a recommendation
- **Scheduled outreach** — proactively push updates, suggestions, event recaps to members
- **Content intelligence** — receives social posts, semantically understands them, generates rewrites/reframes for local context, finds neighbor recommendations

**Mae Agent** = the workflow + campaign orchestration engine
- Campaign builder: who gets what message, when, under what conditions
- Workflow builder: multi-step automations ("new event post → process → find relevant neighbors → SMS them")
- Multi-channel delivery (SMS, email, Slack)
- Human-in-loop approvals for campaigns
- Audit trail

**Social Listener** = new service (needs to be built)
- Subscribes to member socials after ownership verification
- Polls/receives webhooks for new posts (especially events)
- Feeds raw posts into the intelligence layer (community-connector)
- community-connector processes them → hands enriched results to mae_agent to trigger delivery workflows

---

## The Flow

```
Member conversation (community-connector)
  └─ "here's my Instagram" → agent action: register social for listening

Social Listener (new service)
  └─ polls/receives posts from subscribed socials
  └─ sends raw posts to community-connector for processing

Community Connector (intelligence)
  └─ semantic understanding: is this an event? local relevance? 
  └─ generates: rewrite for platform, neighbor recommendations, suggested outreach
  └─ emits enriched payload → mae_agent

Mae Agent (orchestration)
  └─ receives enriched payload
  └─ runs workflow: who to notify, which channel, when
  └─ executes delivery, logs audit trail, gates humans where needed
```

---

## Where Trigger.dev fits

**Social Listener is the natural home for Trigger.dev.** It's exactly the problem Trigger.dev solves:
- Durable polling jobs with retries
- Webhook receiver endpoints
- Scheduled sweeps ("check this account every 15 min")
- Event-driven triggers that fan out to downstream services

Mae_agent (Mastra) handles the agent orchestration once Trigger.dev has done the durable job layer.
