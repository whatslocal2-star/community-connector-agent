The very first thing (after input validation) is **`loadAwaitingOutcome(sessionId)`** — checking Firestore to see if this member has a pending matchLog with `status:"followed_up"`.

If they do, the incoming message is treated as outcome feedback on a past intro, not a normal onboarding turn. The whole normal LLM flow is bypassed and the message routes through `extractOutcome` instead.

So the very first meaningful action is: **"did this person just reply to a follow-up about a match we made?"** That check gates everything else.

Turn 4 [ASSISTANT]:
If the outcome short-circuit doesn't fire, the next step is the **OpenAI call** — `gpt-4o-mini` with the system prompt + full capped history, forced to return `{ reply, profileUpdate }` as JSON.

That's the core onboarding turn: the model reads everything the user has said so far and decides both what to say next and what profile fields to extract.

Turn 5 [ASSISTANT]:

Then fire-and-forget (non-blocking):
- Save any new event subscriptions
- Parse Google Maps URL → lat/lng if a maps link was just captured

---

**On fire-and-forget:** These are async operations that are intentionally not `await`ed:

```js
saveSubscriptions(sessionId, subs).catch(...)          // not awaited
parseGoogleMapsUrl(...).then(...).catch(...)            // not awaited
runCrossRefVerify(...).catch(...)                       // not awaited
enrichProfile(...).then(...).catch(...)                 // not awaited
```

The function returns `{ reply }` to the user **immediately** without waiting for these to finish. They keep running in the background after the response is sent. The `.catch()` on each one prevents an unhandled rejection from crashing anything — errors just get logged.

The tradeoff: the user gets a fast response, but if the Netlify function instance is killed before these finish (e.g. timeout), they silently drop. That's acceptable here because all four are best-effort enrichment — none of them affect the reply the user just received.

The four fire-and-forget operations:

**`saveSubscriptions`** — if the profile now has `eventPostingPlatforms` (e.g. `["instagram", "eventbrite"]`), writes subcollection records under `members/{id}/subscriptions/`. These are what the daily Trigger.dev cron uses to know which channels to scrape for events.

**`parseGoogleMapsUrl`** — if the user just dropped a Google Maps link, sends it to `parseLocation.js` to extract `latitude`/`longitude` and writes them back to the profile. Vendors and organizers are asked for this link so they show up on the marketplace map.

**`runCrossRefVerify`** — once ≥2 contact channels are on the profile (e.g. website + Instagram + phone), fires a Gemini 2.0 Flash grounded search asking "do all these channels describe the same business?" Writes `ownershipVerification` back to the profile if confident. Catches fake/mismatched profiles automatically during onboarding without the user knowing it's happening.

**`enrichProfile`** — only runs once (`enrichedAt` not yet set). Scrapes the member's website via Jina Reader and/or hits Google Places API to pull in any profile fields that are still empty — hours, description, photos, categories, etc. Never overwrites what the user already told us directly.

Turn 13 [ASSISTANT]:
SMS is nearly identical to web but with four key differences:

**1. Signature verification first (line 71)** — before anything else, Telnyx's ed25519 signature is checked. Unsigned requests are rejected 401. Web has no equivalent — it trusts the session UUID.

**2. Idempotency gate (line 105)** — Telnyx retries webhooks on flaky networks and can deliver duplicates. The handler does a Firestore atomic `create` on `webhookEvents/telnyx_{id}` — if another instance already processed this message, `create` throws (doc exists), and the handler bails with `200 OK (duplicate)`. Web doesn't need this because the browser doesn't retry.

**3. Session key is phone number, not UUID** — `fromNumber` is the Firestore doc ID and the key passed everywhere. Web uses a UUID generated in localStorage.

**4. GPT token cap is 300, not 512, and the system prompt enforces "1-3 sentences max"** — SMS is a different register. Web gets slightly more room.

Everything else — outcome short-circuit, normalize prices, save, embed, `shouldRecommend`, cross-ref, ProLocalIQ sync — runs in the same order. The one thing missing from SMS vs web is `enrichProfile` and `saveSubscriptions` — those fire-and-forget calls from `chat.js` aren't here.
