Correct — nothing is persisted right now. The conversation history lives only in the browser's `history` array and disappears when the tab closes.

Your instinct on document DB is right. Here's the tradeoff:

**Firestore (Firebase)** is the best fit here — true document DB, generous free tier, and each member type becomes its own collection of documents with whatever fields apply to that type. Querying across collections for matching (e.g. "find artists in Brooklyn open to collabs") is straightforward. Works well in Netlify functions via the Firebase Admin SDK.

**MongoDB Atlas** is a close second — same flexibility, more powerful aggregation queries if the matching logic gets complex. Free tier is slightly less generous.

**Netlify Blobs** — already in your `package.json` — is the path of least resistance for a prototype but it's a key-value store, not a real DB. You can't query it ("give me all artists in NYC"), only fetch by key. Good for storing individual sessions, bad for matching across members.

**My recommendation: Firestore for anything beyond a demo.** The flexible schema handles your five member types cleanly (each has different fields), the free tier covers a lot of traffic, and you already need real-time capabilities later for the anonymous match approval + chat flow.

Turn 40 [ASSISTANT]:
Honestly, not quite. The two-GPT-calls-per-turn approach I described has real problems:

- **Extra latency and cost** on every single message
- **Unreliable extraction** — having GPT re-parse its own conversation to pull out fields it already knows is wasteful and error-prone

**The better way: OpenAI function calling (structured outputs)**

Instead of a separate extraction step, you make the model emit structured profile data *alongside* its reply in a single API call. The model already knows what it just learned — you just ask it to also return it as typed JSON:

```javascript
const completion = await client.chat.completions.create({
  model: "gpt-4o-mini",
  messages: [...],
  tools: [{
    type: "function",
    function: {
      name: "update_profile",
      description: "Upsert any profile fields learned from this turn",
      parameters: {
        type: "object",
        properties: {
          memberType: { type: "string" },
          location: { type: "string" },
          portfolioLink: { type: "string" },
          disciplines: { type: "array", items: { type: "string" } },
          venueTypes: { type: "array", items: { type: "string" } },
          eventPlatforms: { type: "array", items: { type: "string" } },
          // etc.
        }
      }
    }
  }],
  tool_choice: "auto"
});
// one call → reply text + structured profile delta
```

One round trip. No re-parsing. The model only populates fields it's confident about from this turn, you upsert those into the profile document.

**The storage architecture is still right** — Firestore with one document per user, conversation history + profile fields side by side. For SMS, Twilio phone number is the key. For in-app chat, your user ID.
