**Community Connector Agent** (Netlify/Firestore/Pinecone):

**The identity problem** — the same person could exist as:
- A Supabase user (email, `user.id`)

- A Firestore member doc keyed by phone number

Zero overlap by default.

## Plan

### Phase 1 — Plug the agent into localloop

**Replace `business-onboarding.tsx`'s static form** with a conversational onboarding chat powered by the community-connector agent. Instead of a blank form, the user gets the warm onboarding conversation, and the profile data is captured by the agent.

**Replace (or back) the two Supabase Edge Functions** (`business-assistant`, `shopper-assistant`) with calls to the community-connector agent's logic. **Backend move decision:** Two options:
- A) Keep Netlify, localloop calls it over HTTP (simple, works today)
- B) Migrate `chat.js`/`sms.js` into Supabase Edge Functions (collocates with localloop's existing edge functions, one deploy target)

Recommended: **A first, then B** — get it wired first, migrate later.

### Phase 2 — Identity merge (phone + email → same user)

This is the core design problem. The merge keys are:

| Source | Identity key | Available |
|--------|-------------|-----------|
| Localloop signup | `supabase user.id` + email | Always |
| SMS conversation | phone number | Always |
| Web chat (pre-login) | random `sessionId` | Ephemeral |

**The merge flow:**

1. **Phone verification in localloop** — add phone to the Supabase user profile (Supabase supports phone as a second auth factor). On verification, look up any Firestore member doc by that phone number → merge profile fields into the user's canonical record.

2. **Post-chat claim** — after an anonymous web chat, when the user logs in or signs up, pass the `sessionId` to the backend → merge that Firestore doc into their `user.id` record.

3. **SMS → account link** — when an SMS user later creates a localloop account with the same phone, auto-link on first login.

**Canonical identity** lives in Supabase. Firestore gets a `supabaseUserId` field added when any link is established.

### Phase 3 — Storage consolidation (optional, later)

Supabase has pgvector. Long term you could migrate off Firestore + Pinecone → Supabase Postgres + pgvector, which lets you JOIN member profiles with localloop's `businesses` and `users` tables natively. Not needed for Phase 1-2.

**WorkOS** is enterprise B2B — SAML, SCIM, SSO for company logins. Nothing about this stack is enterprise. Wrong tool entirely.

**Clerk** is genuinely good for consumer apps and has solid React Native support, but the problem is localloop already has Supabase auth wired throughout (`useAuth`, `supabase.from(...)` with RLS, `user.id` as FK everywhere). Migrating to Clerk would mean ripping all of that out and rebuilding the auth layer for zero net gain — Clerk doesn't give you anything Supabase auth can't do here.

**Supabase auth already handles your exact needs:**

| Need | Supabase auth support |
|------|----------------------|
| Email + password | Native |
| Phone OTP (SMS) | Native — Telnyx or Twilio as provider |
| Link phone to existing email account | `supabase.auth.updateUser({ phone })` + OTP verify |
| Anonymous session → claimed account | `signInAnonymously()` + `linkIdentity()` |
| SMS user creates email account later | Match on phone at signup |

The anonymous web chat → claimed account flow maps perfectly onto Supabase's `signInAnonymously()` — the web chat widget starts an anonymous Supabase session, gets a real `user.id`, and when the user later signs up you call `linkIdentity()` to merge them. No sessionId juggling in Firestore needed.
